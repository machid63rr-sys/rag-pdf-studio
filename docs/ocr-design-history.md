# OCRパイプラインの設計決定の履歴

コピー元システム（anomaly-detection、コミット523b094時点）の `src/manuals/ocr_pipeline.py` 冒頭に
書かれていた説明を、原文のまま移したもの。**現行の仕様は `ocr_rag/ocr/ocr_pipeline.py` の冒頭を参照**。
ここには、各決定に至った実機検証の経緯が残っている（GLM-OCRが主文だった時代の記述を含む）。

```text
vision LLM(主文) + GLM-OCR(比較) + diff + vision補正の全体オーケストレーション

ページ単位で以下を行い、下書きMarkdown（draft_markdown）とフロントの差分ハイライト
プレビュー用データ（diff_segments）を組み立てる:
1. vision LLM(既定qwen3.5:9b)でフルページOCRする（temperature=0、これが主文）
2. GLM-OCRを1回実行する（比較候補。別モデルなので同じ誤りを共有しにくい）
3. 正規化してdiff（低信頼度箇所検出）
4. 不一致セグメントのあるページのみ、画像+両候補をvision LLMにまとめて渡し判定
5. 自動修正(status=auto_corrected)/要確認(status=needs_review)/一致(status=match)を
   組み立て、最終的なdraft_markdownは主文(vision LLM)をベースに自動修正箇所だけ
   置換する。still_uncertain=Trueの箇所はLLMの提案を採用せず主文を暫定採用する
   （画像を見ても判定できない=信頼できる根拠が無い、ため保守的に倒す）。

セグメントのglm_text/glm_alt_textキーは旧方式(GLM-OCR 2回実行)時代の名前で、
現在の意味は glm_text=主文候補(vision LLM)、glm_alt_text=比較候補 である
（保存済みdraft(JSONB)・フロント型との互換のためキー名は変えていない）。

モデル名は呼び出し側(src/api/routers/manuals.py)が環境変数
OCR_VISION_MODEL(主文) / OCR_MODEL(比較のGLM-OCR)から渡す。コード変更なしで差し替え可能。

以下は経緯の履歴。(3)〜(11)はGLM-OCRを主文としていた時代の記述を含む。
現在の構成は末尾の2026-09-30(12)決定を参照。

2026-09-29(3)決定、下記参照）
2. 正規化してdiff（低信頼度箇所検出）
3. 不一致セグメントのあるページのみ、画像+両候補をvision LLMにまとめて渡し判定
4. 自動修正(status=auto_corrected)/要確認(status=needs_review)/一致(status=match)を
   組み立て、最終的なdraft_markdownは1回目のGLM-OCR出力をベースに自動修正箇所だけ
   置換する。still_uncertain=Trueの箇所はLLMの提案を採用せず1回目の候補を暫定採用する
   （画像を見ても判定できない=信頼できる根拠が無い、ため保守的に倒す）。

2026-09-29(3)決定: 低信頼度検出は当初tesseract(比較専用の補助信号)との
diffで行っていたが、実マニュアルで検証したところtesseractの日本語認識精度が
低く、GLM-OCRが正しく読めている箇所まで「tesseractと食い違う」という理由で
軒並み要確認扱いになってしまう問題が判明した（ユーザーが実際に試して確認）。
そのためtesseractとの比較をやめ、GLM-OCR自体を異なるtemperature/seedで2回
走らせてその2回分をdiffする方式に変更した。

GLM-OCR応答が打ち切られた場合(ocr_engines.py参照)、そのページの先頭に
status=needs_reviewの目印セグメントを追加してページ全体を要確認扱いにする
（打ち切りまでの内容自体は活かす。ドキュメント全体は失敗させない）。

2026-09-29(4)決定: 1回目が打ち切られた場合、結論(ページ全体要確認)は既に
確定するため2回目は実行しない（無駄なレイテンシ増を避ける）。

2026-09-29(5)決定: 1回目が打ち切られた場合、その時点の部分応答だけで諦めず、
qwen3.5:9b(汎用vision対応LLM)にページ画像をフルページOCRさせる最終手段を追加した
（過去のマニュアル取込では、複雑な表・特殊文字を含むページはAIが画像を直接見て
書き起こしていた実績があり、同じ手法を自動化する）。

2026-09-29(6)決定: 上記フォールバックが成功した場合、画像と書き起こし結果を
再度照合させる(verify_full_page_ocr_with_vision_llm)。

2026-09-29(7)決定: 検証で一致確認できた場合はneeds_reviewを外し、不一致が
見つかった場合も、検証結果のcorrected_textをocr_text/glm_alt_text相当として
既存のdiff_page()+セグメント単位補正にそのまま渡す。ページ全体を一律
needs_review扱いにすると正しく読めている大部分まで巻き込んでしまい人手確認の
手間が減らないという実機フィードバックへの対処（検証呼び出し自体が失敗した
場合のみ、有効な修正案が無いため保守的にページ全体をneeds_review扱いにする）。

2026-09-29(10)決定: qwen3.5:9bの自己検証(matches_image)は、初回OCRと自己検証が
同じ誤り(簡体字混入・誤字等)に一致してしまい検出できないケースが実機検証で
判明した。GLM-OCR(別モデル)の打ち切りまでの部分応答が残っている場合は、
自己検証より優先してそちらとdiffする（モデルが異なれば同じ誤りを共有しにくい）。

2026-09-29(11)決定: GLM-OCRが表を書いている途中で打ち切られた場合、部分応答
自体の表構造が壊れていて比較材料として使い物にならず、判定漏れ
(MISSING_JUDGMENT_REASON)が多発することが実機検証で判明した。判定漏れの件数で
比較材料の適否を診断し、不適な場合はGLM-OCRの部分応答を使わず、
qwen3.5:9bをもう一度異なるtemperature/seedで実行して自己比較する
(2x-GLM-OCRと同じ仕組み)方式にフォールバックする。

2026-09-30(12)決定: 主文をGLM-OCRからvision LLMに切り替えた。従来はLLMが
「GLM-OCR 2回の結果が食い違った箇所」しか見ないため、GLMが2回とも同じ誤読をした
箇所（例: ①などの環境依存文字の誤読・欠落）は一致扱いでLLMに渡らず、プロンプトを
強化したLLMの精度が最終結果に効かなかった。(5)(10)(11)の「GLM打ち切り時の
フォールバック」経路(LLM主文+GLM比較→判定漏れ多発ならLLM自己2回diff→自己検証)
を全ページの標準経路に昇格し、GLM-OCRは2回実行から比較用の1回実行に変更した。
LLMのフルページOCR自体が失敗した場合のみGLM-OCRを暫定主文とし、ページ全体を
要確認扱いにする（サイレントに採用しない）。

2026-09-30(13)決定: GLM-OCRとの比較が使えないかの判定(自己比較へのフォールバック)を、
「判定漏れ」だけでなく補正LLMが確定できず要確認になったセグメント全般の件数で行う
（MAX_UNRESOLVED_SEGMENTS_FOR_PARTIAL_DIFFのコメント参照）。

2026-10-05(14)決定: vision LLMが同じPDFでも実行ごとに表の書き方を揺らし、ヘッダ行と区切り行の
列数が食い違って画面で表として表示されない下書きが5件中3件あった。差分判定の前(OCR結果の入口)
の normalize_ocr_markup で、文言を捨てない範囲の表の修復を行う（table_repair.py参照）。
入口で直すため、segments(final_text)とdraft_markdownの整合は崩れず、崩れた表の構造差が
要確認の誤検出になることも減る。直せない表は画面(Step3)側で警告する。
```
