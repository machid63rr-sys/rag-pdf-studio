# 構成と設計の判断

## 全体像

```
ブラウザ ── app（Node/React） ───────────────┐ 画面と、PDF生成(Chromium)
              │  /api/rag/* を中継           │
              ▼                              │
           ocr-rag（Python/FastAPI）         │
              │            │                │
        postgres(pgvector)  ollama           │
        文書・チャンク・     OCR(vision LLM +  │
        原本PDF・OCR下書き・ GLM-OCR)・埋め込み │
        チャットの会話       ・チャットの回答   │
```

| サービス | 役割 | 外部への公開 |
|---|---|---|
| app | 画面（4機能のタブ）、MD/HTML→PDFの生成、`/api/rag/*` の中継（チャットの回答のストリームも、溜めずに中継する） | ブラウザ用の1ポートのみ |
| ocr-rag | OCR・RAG登録・検索・チャットのAPI | なし（appだけが接続する） |
| postgres | pgvector。文書・チャンク・原本PDF・OCR下書き・チャットの会話 | なし |
| ollama | `qwen3.5:9b`（OCR主文・チャットの回答）、`glm-ocr`（OCR比較）、`bge-m3`（埋め込み） | なし |

## 4つの機能と、データの流れ

```
 スキャンPDF ──②OCR──▶ 下書きMarkdown ──人が確認・修正──▶ 確認済みMarkdown
                                                       ├─▶ ①でPDFに整えて出力（MD/PDF）
                                                       └─▶ ③でRAGに登録 ──▶ 検索で確認
```

- ②の結果は、そのまま①（PDFにして出力）・③（RAG登録）へ渡せる。ファイルを介して渡すこともできる（③は任意のMarkdownを登録できる）。
- ③は、OCRとは独立している。手書きのMarkdownも登録できる。
- ④（チャット）は、③で登録した内容を、質問のたびに自動で検索して回答する。登録が増えれば、そのまま回答の根拠が増える。

## チャットは、検索と生成を同期的に流す

OCRと違い、チャットは会話の応答なので、バックグラウンドにせず、1回のHTTP呼び出しの中で、検索 → 生成を行い、結果をストリーミングで返す。

```
質問 ─▶ 機器名の解決 ─▶ 埋め込み検索(top 5) ─▶ 類似度0.45未満を除く ─┬─ 1件以上 ─▶ 抜粋をsystemに入れて /api/chat(stream)
                                                                   │                                  │
                                                                   └─ 0件 ─▶ 固定の「記載がありません」    │
                                                                              （LLMは呼ばない）            │
        画面 ◀── manual_references → delta … → done(回答を保存) ◀─────────────────────────────────────────┘
```

- 回答の根拠は、検索で見つかった抜粋だけ。しきい値に届かない抜粋は、根拠にも参照マニュアルにも出さない（無関係な資料を、根拠のように見せないため）。
  「マニュアルを見せて」のような直接の質問だけ、しきい値を外し、その質問用の指示をプロンプトに足す（文面と資料本文の意味が近くなりにくく、資料があっても0件になるため）。
- **根拠が1件も無いときは、LLMを呼ばない**。「抜粋が無ければ、無いと答えよ」とプロンプトで指示しても、実モデル（qwen3.5:9b）は、資料に無い回答を作り、存在しない資料を引用した。
  指示に頼らず、固定の回答を返す。検索に失敗したときも、失敗をモデルに伝えて続けさせず、エラーにする（根拠なく回答を作らせない）。
- しきい値は0.45。短い質問では、該当する記載を含むチャンクでも類似度が0.47まで下がり（0.5では、正解を落とした）、範囲外の質問の最大は0.42だった（暫定）。
- プロンプトは、特定の業界・用途に限らない（元は空調設備の保守員向けだった）。このアプリは、登録した資料一般に使えることを目的とする。
- 機器名は、質問文の言及を最優先し（完全一致 → 英数字の前方一致で、1つに決まるときだけ）、無ければ会話に設定した機器名で絞る。
- 回答は、最後まで生成できたときだけ保存する。停止・失敗した回答は保存せず、質問は残す。画面が切断したら、Ollamaへの接続を閉じて生成を打ち切る。
- LLMには、直近の履歴を約3000文字まで送り直す（`/api/chat` はステートレス。全履歴を送ると、会話が長くなるほどコンテキストを使い切り、回答が途中で切れる）。表示・保存は全履歴のまま。
- コンテキスト長は、OCRの主文と同じ値にそろえている。違う値で呼ぶと、Ollamaが同じモデルをロードし直し、OCRとチャットを行き来するたびに待たされる。

## OCRは、バックグラウンドで実行する

OCRは1ページ数分かかる（複数ページなら10分を超える）。HTTPの1回の呼び出しで最後まで待たせると、
プロキシ・ブラウザのタイムアウトや、画面を閉じたときの喪失で壊れやすい。そのため、
`POST /ocr-drafts` は下書きを登録して即座に `202` で返し、実行は `ocr-rag` の別スレッドが行う。
画面は、状態と進捗を見に行く（リロードしても、同じ下書きを開き直せる）。

```
QUEUED(順番待ち) ──▶ RUNNING(実行中。pages_done/page_count で進捗) ──▶ DRAFT(完了。人が確認・修正)
      │                       │                                          └─▶ DISCARDED(破棄)
      └────────┬──────────────┴──▶ FAILED(失敗。error_message に理由)
               └─▶ DISCARDED(破棄。実行中なら、現在のページの処理が終わった時点で中止)
```

- OCRはGPU（Ollama）を占有するため、**同時に1件だけ**実行する。残りはQUEUEDで待つ。
- 実行中のOCRは、ページの区切りで中止できる（ページの途中では止まらない）。
- サーバーが停止・再起動すると、実行中・待機中の下書きは再開できない。起動時にFAILEDにして、画面に
  「中断された」と表示する（黙って放置しない）。パスワード（暗号化PDF用）はメモリ上だけで持ち、DBには保存しない。
- OCRの中身（vision LLMが主文を読み、GLM-OCRと比較し、食い違いだけを補正する）は
  [ocr-design-history.md](ocr-design-history.md) に、決定の経緯がある。

## 設計の判断（主なもの）

| 判断 | 理由 |
|---|---|
| 検索は埋め込み検索のみ（リランクなし） | 登録内容の確認には十分だった（8文書・107チャンクの10問で、正解が3位以内10件）。リランクはtorch等が重いため、後から足す。チャットも同じ検索を使うため、短い質問では類似度が低く出て、資料があっても「記載なし」になることがある（類似度のしきい値は暫定。実際のマニュアルでの再確認が要る） |
| チャットは、浮動ウィジェットではなく、他の機能と同じタブ | 元の異常検知システムでは、どの画面からも開けるよう右下の浮動ウィジェットだった。ここでは、特定の画面（異常イベントの詳細）に結びつく文脈が無く、機能ごとのタブに合わせた |
| チャットの会話は、認証が無いため全員で共有する | 元システムはユーザーごとに会話を分けていた。このアプリには、ユーザーの区別が無い |
| チャットの履歴の原本PDFリンクは、回答時点の文書IDを控えたもの | 同じ登録名で登録し直すと、文書IDが変わる。古い会話の「原本PDFを開く」は、404になることがある（後から検索し直すと、回答の根拠が変わってしまうため、控えを残す） |
| 機能を足したときのテーブルの追加は、`database/migrations/` のSQLを手で流す | `schema.sql` は空のDBへの初回起動でしか適用されない。専用の仕組み（バージョン管理）は、変更が増えたときに導入する。足りないときは、APIが503で手順を返す |
| 埋め込みを、DB書き込みの前に全チャンク分行う | Ollamaの停止などで失敗したとき、既存の登録を消さずに止まるため |
| 同名ファイルの再登録は置き換え（原本PDFは引き継ぐ） | 部分更新はしない。DBの一意制約で、同名の重複を防ぐ |
| 機器名なしの登録は、全機器共通の資料 | 機器名で絞った検索にも、常に含める |
| 認証なし・既定は127.0.0.1のみ公開 | 単体利用の前提（md-pdf-editorと同じ）。複数人で共有する場合は、認証を別途用意する |
| モデルは初回起動時に取得（約10GB） | 以降はオフラインで動く。`down -v` でモデルのボリュームが消えると、再取得が必要 |
| 画面からは `/api/rag/*` だけを使い、ocr-ragを直接公開しない | 同じオリジンなのでCORS不要。公開面を1つにし、許可したパスだけを中継する（`/docs` は中継しない） |

## 元システムとの関係

異常検知システム（`anomaly-detection`、コミット `523b094`）のOCR・RAG・チャット部分と、md-pdf-editor（コミット `fead8e7`）を、
それぞれ**コピーして**再作成したもの。元のリポジトリは変更していない。
修正を両方に入れたい場合は、コピー先（このリポジトリ）と元で、別々に行う必要がある。
